# V3.5.03 代码风险检视

## 1. 范围与结论

本轮只读检视了主生成器 `xlsx2verilog.py`、独立 merger `appendix/xlsx2verilog_merger.py`、现有单元测试及边界工作簿。本轮不修改 Python 代码。

总体结论：默认配置下的主路径已有较完整的文本回归，且定向执行的 22 个宽度/parameter 测试全部通过；主要风险集中在“打开 parameter 自动位宽适配后的多维切片”“参数默认值与 elaboration override 的差异”“inout 驱动识别”以及“显式 parameter 互连的 localparam 命名歧义”。merger 的事务写入和失败保护较稳健，但仍受正则/单行语法及重复 USER 段 occurrence 键限制。

严重度定义：

- 高：可能生成越界、非法或错误连接，且文本生成仍可能成功；
- 中：语义容易与用户预期不一致，或在特定输入上造成错误/合并中止；
- 低：维护性、可移植性或诊断质量问题。

“已确认”表示从现有代码可直接证明；“待复现”表示存在完整可达路径，但尚无对应的最小编译回归。

## 2. 主生成器风险

### R-01 高：parameter 自动适配固化 XLSX 默认值

- 状态：已确认设计边界。
- 条件：`AUTO_ZERO_FILL_PARAMETER_WIDTH_MISMATCH=True`，连接含 parameter，且上下层匹配值不同。
- 路径：`resolved_width_value()`读取 `Width.default`，`packed_total_width()`据此计算总宽，`fit_source_width()`生成定宽补零或固定 part-select。
- 现象：若 Verilog elaboration 时又 override 了 parameter，生成的 `{4'b0, ...}`或 `[12 -1:0]`仍保持 XLSX 默认差值，可能不再等宽，甚至越界。
- 当前缓解：开关默认关闭；始终产生 `W_PARAMETER_WIDTH_MISMATCH`。
- 建议：长期方案应优先生成参数表达式形式的差值/总宽，或只在所有相关 parameter 被锁定为 TOP 正文 localparam 时允许自动适配。短期至少增加“默认 8、实例 override 16”的编译测试。

### R-02 高：TOP 多维 rvalue 截断没有先扁平化

- 状态：可达，待最小编译复现。
- 条件：开关打开；TOP 多维 parameter 信号驱动 child input；总位宽不同且需要截断。
- 路径：TOP 表达式仍是多维信号名，`fit_source_width()`直接调用 `low_bits(expression, target_total)`。
- 可能输出：对 `[2][6]`信号生成 `top_signal[8 -1:0]`。该范围选择作用在最左 packed 维，而不是一个 12 bit 扁平向量；索引 7 可能超过最左维上界 1。
- 对比：child output 驱动 TOP 的多维路径已通过 `flattened_port_width()`先建一维 adapter，本路径尚未对称处理。
- 建议：所有“总 bit 数 resize”统一经过显式一维 adapter，或使用 streaming/类型转换并以目标工具链验证。

### R-03 高：`[i]`后的实际宽度仍可能按完整端口计算

- 状态：可达，待最小编译复现。
- 条件：TOP 引用 `signal[i]`，原信号有外层维度，并同时触发宽度适配。
- 路径：连接表达式先变为 `signal[generated_index]`，但 `top_width`仍来自完整 `Port`的 `connection_numeric_width()`；“总宽相同直连”优化也因存在 `top_index`而关闭。
- 现象：脚本可能把一个元素当成整个数组总宽，再生成错误的截断或补零。
- 建议：引入“连接表达式形状”，bit/index select 后先从端口形状中消费相应维度，再比较和适配。不要继续仅传 `Port + expression string`。

### R-04 高：内部多维 parameter 网络可能按总宽直接 range-select

- 状态：可达，待最小编译复现。
- 条件：开关打开；后续连接区有唯一 output；多维 parameter 总宽大于某个 input 总宽。
- 路径：内部 wire保留多维形状，`parameter_inline_adapter`分支对较窄 input 调用 `low_bits(wire, input_total)`。
- 现象：与 R-02 相同，part-select 落在最左维，而不是扁平总线，可能越界。
- 建议：内部 parameter 网络也使用统一 flat adapter；至少补充“output [2][6] -> input [2][4]”编译回归。

### R-05 高：inout 不计入内部网络驱动端

- 状态：已确认。
- 条件：后续连接区含 inout，但没有 direction=`output`的端点。
- 路径：driver 列表仅筛选 `port.direction == "output"`。
- 现象：脚本产生 `W_DRIVER_RISK`后仍可能对该 wire 赋 0；inout 外部也可能驱动同一网络，形成额外驱动或改变总线语义。
- 建议：为普通 output、inout、interface 分开建立驱动模型。inout 网络不应自动补固定驱动，除非规格明确要求 pull/tie-off。

### R-06 中：`add_top_local_parameter()`实际生成 module parameter

- 状态：已确认。
- 条件：显式 parameter 互连只有子模块端点，没有 TOP parameter、NA 或直接值。
- 路径：函数把参数写入 `top.parameters`；`render_module_header()`最终在 `module #(...)`输出 `parameter`。
- 现象：函数名、info 文本和历史测试名都称其为 localparam，但生成结果扩大了 TOP 的外部可配置接口。
- 风险：用户可能认为值已锁定，实际仍可被上层 override。
- 建议：先明确产品规格。若应为正文 localparam，改用 `add_integration_local_parameter()`；若应暴露为 module parameter，则重命名函数和诊断，并修正文档/测试名。

### R-07 中：纯 literal/macro 多维 mismatch 与 parameter 多维策略不对称

- 状态：已确认。
- 条件：连接双方是多维，但不含 parameter。
- 路径：`simple_packed_width()`遇到 `arrays`或 `packed_dimensions`直接返回 `None`。
- 现象：多数路径只 warning 后直接连接；而 parameter 多维在开关打开时会按总宽尝试 adapter。
- 风险：相同的 packed 总宽问题因维度来源不同而得到不同代码，用户难以预测。
- 建议：把“是否能安全 resize”与“维度是 literal/macro/parameter”解耦；统一使用完整 shape/total API，再由策略决定是否自动改写。

### R-08 中：等总宽的维度重排不是矩阵转置

- 状态：刻意行为，容易误用。
- 条件：如 `[2][6]`直接连接 `[6][2]`。
- 行为：warning 后不建 adapter，按 12 个 packed bit 的线性顺序传递。
- 风险：若业务把两维解释为行/列，线性重解释不等于交换两个维度。
- 建议：文档和 warning 中明确“仅 bit 数兼容，不保证维度语义”；真正 transpose 应由用户逻辑完成。

### R-09 中：相同默认总宽可能掩盖未来 override 差异

- 状态：已确认设计边界。
- 条件：两端由不同 parameter/macro 表达，但 XLSX 匹配值乘积相同。
- 行为：形状 warning 仍存在，但“总宽相同”会绕过 adapter并直连。
- 风险：后续独立 override 后总宽可能不再相同。
- 建议：只对符号来源等价或明确锁定的参数使用“等总宽直连”优化；否则保留 elaboration 风险诊断。

### R-10 中：直接 parameter `i/o`的表达式语法不统一

- 状态：已确认。
- 条件：集成 parameter 行 `i/o`写 `A+1`、`` `FUNC(A)``等。
- 行为：模块页 parameter 表达式支持这些形式，但集成直接 override 只接受自然数或单个反引号宏，其他形式报 `E_PARAMETER`。
- 建议：若这是安全限制，应在错误中称为明确规格；若期望统一，则复用 `normalize_parameter_expression()`并增加注入防护测试。

### R-11 中：未知模板宽度 114 是可编译但可能掩盖错误的占位

- 状态：刻意行为。
- 条件：模板、宏或 parameter 默认值无法确定且路径允许 fallback。
- 行为：生成 `[114 -1:0]`并 warning。
- 风险：非 strict 流程仍能产生看似完整的 RTL，114 可能继续传播到 wire 和 adapter。
- 建议：生产 CI 使用 `--strict`，或增加“禁止占位值”的独立质量门禁，而不是依赖所有 warning 一刀切。

### R-12 中：零位宽保留不具工具链可移植性

- 状态：刻意行为。
- 条件：显式位宽或匹配值为 0。
- 行为：输出 `[0 -1:0]`与 `W_ZERO_WIDTH`，不参与 adapter。
- 风险：不同编译器可能拒绝、解释为异常范围或产生非预期位数。
- 建议：量产环境把 `W_ZERO_WIDTH`单独设为阻断条件。注意“空白位宽 + 数值 0”仍是标量 1，与显式 0 不同。

### R-13 低：`render_integration()`职责过大且会修改模型

- 状态：已确认维护风险。
- 事实：该函数超过两千行，包含 parameter 解析、NA、方向、宽度、generate、命名、诊断和最终渲染；内部闭包共享多个可变字典。显式 parameter 链接还会在渲染阶段修改 `top.parameters`及子模块的可配置集合。
- 风险：分支间顺序耦合强，修复一种连接容易改变其他路径；函数级单元测试难隔离。
- 建议：先建立不可变的 `ConnectionPlan`/`ResolvedShape`中间模型，再把“规划”和“文本排版”拆开。此项属于重构，不应与紧急 bugfix 同批实施。

### R-14 低：历史位宽文档已经与当前 warning 数量和 parameter 行为偏离

- 状态：已确认。
- 现象：旧《V3.2 位宽不匹配分析》记录的是当时策略；当前边界工作簿产生 13 条 warning，且 parameter 多维已有可选 adapter。
- 当前处理：本轮新增《V3.5.03 位宽行为矩阵》，README 不再把旧 warning 数量当成当前规格。旧文档保留为历史记录。

## 3. merger 风险

### M-01 高：同标签 USER 段仍以 occurrence 匹配

- 状态：已确认算法边界。
- 条件：一个模块中重复出现相同 USER 标签，并在新生成结构的前部插入/删除同标签段。
- 路径：USER region 的稳定键是 `(label, occurrence)`。
- 现象：旧第 N 段可能映射到新第 N 段，但它们对应的实例已经改变；若标签内容都非空，算法未必能识别语义错位。
- 建议：实例前后 USER 段把实例身份写入 marker key，或建立 module/instance/label 三元键；只把 occurrence 留给旧文件兼容回退。

### M-02 中：`//USER:`只支持可识别的完整单行语句

- 状态：已确认规格限制。
- 支持：单行 assign、wire/reg、localparam/parameter、单行 named-port connection、genvar/generate/endgenerate。
- 不支持：跨行 assign、多行声明、复杂 procedural statement、logic/tri 等其他 net/data type。
- 行为：无法识别时在写入前失败，安全性优于静默丢失，但生产用户可能在改写格式后突然无法 merge。
- 建议：README 明确“单行契约”；若需要扩展，应使用 token/AST parser，而不是继续堆叠正则。

### M-03 中：保留整行人工 assign 可能与新宽度结构冲突

- 状态：刻意行为。
- 条件：旧 assign 带 `//USER:`，新生成版本改变 LHS/RHS 相关声明宽度。
- 行为：merger 以 key 找到新 assign 后，用旧整行替换。
- 风险：人工表达式被完整保留，但可能产生越界、截断或对已删除信号的引用。
- 当前缓解：找不到 key 时 merge 失败；找到同根信号的候选有歧义时 warning或失败。
- 建议：merge 后增加编译/lint阶段；merger 本身不应猜测如何重写用户逻辑。

### M-04 中：正则解析不是完整 Verilog/SystemVerilog 语法

- 状态：已确认架构限制。
- 条件：宏展开改变行结构、字符串中含注释样式、非 ANSI/复杂 ANSI 声明、属性或多行 named association。
- 现象：模块、声明、实例或注释边界可能无法识别，从而保留失败或错误匹配。
- 建议：限定 merger 输入为本生成器输出风格；要支持任意生产 RTL 时改用成熟 SystemVerilog parser。

### M-05 低：声明类型保护范围只有 wire/reg

- 状态：已确认。
- 行为：满足当前“生成 wire、用户可改 reg”的需求，但不会保留 `logic`、`tri`、`wand`等类型迁移。
- 建议：不要在文档中泛称“保留所有声明类型”；若扩展，先定义 net type 与 variable type 的合法上下文。

### M-06 低：merger 的文本策略正确性依赖后续编译

- 状态：架构事实。
- 优点：计划、备份、暂存、原子替换和失败回滚降低文件损坏风险。
- 缺口：当前核心测试主要断言文本和诊断，不等于 SystemVerilog elaboration 成功。
- 建议：生产流水线把 merger 输出送入项目真实 compiler/linter；Beyond Compare 仅用于人工观察，不能作为正确性判定。

## 4. 建议补充的最小回归

| 优先级 | 测试 | 期望 |
|---|---|---|
| P0 | AUTO=True，TOP `[P=2][Q=6]` input -> child `[P=2][R=4]` input | 不在最左维上生成 `[8 -1:0]`；编译通过 |
| P0 | AUTO=True，内部 output `[2][6]` -> input `[2][4]` | 使用安全扁平 adapter；编译通过 |
| P0 | `[COUNT][DW] signal[i]`连接单实例端口 | 比较的是索引后元素宽度 DW |
| P0 | inout + input 内部网，无 output | 不自动添加固定 0 驱动 |
| P1 | XLSX 默认 8，实例/上层 override 16 | 自动 adapter 不固化错误差值，或明确拒绝 |
| P1 | `[2][6]` -> `[6][2]` | 保持直连和 warning，并在测试名中注明非 transpose |
| P1 | 只有两个 child parameter 的显式链接 | 根据最终规格断言 module parameter 或正文 localparam |
| P1 | merger 在重复同标签实例前插入新实例 | USER 段按实例身份保留，不按 occurrence 错位 |
| P2 | `//USER:`多行/logic 输入 | 明确拒绝信息稳定，或在扩展 parser 后支持 |
| P2 | 0 宽在项目使用的 simulator/synthesizer 中编译 | 记录工具链实际行为 |

## 5. 修复顺序建议

1. 先处理 R-02、R-03、R-04、R-05，并以真实 SystemVerilog 编译而非只看字符串。
2. 决定 R-06 的产品语义，再统一函数名、诊断、README 和测试名。
3. 设计 parameter override 安全策略，处理 R-01/R-09，之后再考虑默认开启自动适配。
4. 用统一 `ResolvedShape`消除 R-07，并逐步拆分 `render_integration()`。
5. merger 优先升级 USER region 的实例身份键，再考虑扩展语法范围。

代码瘦身与拆分顺序见[《V3.5.03 代码瘦身规划》](V3.5.03代码瘦身规划.md)。
